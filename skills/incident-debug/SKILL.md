# 排查 bot 异常

顺序不可跳步。每一步的结论决定下一步做什么，跳过任一步都可能把可救的状态丢掉。

## 1. 端口

```bash
ss -tln | grep -E ':(22|3000|3001|8899)'
```

## 2. 应用层

```bash
curl -s -o /dev/null -w "%{http_code}\n" --max-time 8 http://127.0.0.1:8899/health
docker logs pi-rt --tail 20
```

## 3. 资源

```bash
free -m
docker stats --no-stream
```

## 判断表

| 现象 | 结论 | 动作 |
|---|---|---|
| 端口 OPEN + HTTP 返回 `000` | 整机卡死（内核活着，用户态卡住） | 控制台 VNC / 重启实例 |
| 端口 closed | 容器没起 | `docker ps -a` 看状态与 restart 策略 |
| 日志有 `[event #N]` 但用户没收到回复 | 发送层问题 | 查 token / 权限 / `FEISHU_CHAT_ALLOW` 白名单 |
| 日志完全没有 event | 消息没进来 | 群聊看是否 @ / 唤醒词 / 白名单 |
| `swap` 用量持续上涨 | 内存压力 | 先停最肥的容器，再看是否需要升配 |

## 禁止

- **没有做完 1–4 就 `docker restart`**：重启会丢掉正在进行的任务，且掩盖根因。
- 把「应该是内存问题」当结论：用 `free -m` 证明。
- 连续重试同一条命令当排查：换个观测面（端口 → 日志 → 资源）。

## 收尾

定位到原因后，把结论写进事件或工单，并补一条能复现的检查。**同一个故障不应排查第三次。**
